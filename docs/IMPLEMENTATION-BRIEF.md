# Implementation brief — v0

Sources: ARCHITECTURE.md, DATA-MODEL.md, SECURITY-CONTROLS.md, TESTING-STRATEGY.md, INTEGRATIONS.md, ADR 0002, ADR 0004. Field names, enum values and class tags are quoted exactly. `[D]` = the spec implies but does not state it; it is an implementation decision (see §6).

Content classes: `CONTENT` (never logged, encrypted at rest, deleted per retention, minimised before a provider), `IDENTITY` (never logged in plain form, pseudonymised in prompts), `METADATA` (loggable, survives content deletion), `SECRET` (per-workspace key; never logged, rendered, exported or sent to a provider).
Retention classes: `R-EPHEMERAL` (<=7d), `R-CONTENT` (30d default, 7-90 per workspace), `R-DERIVED` (12mo default, 3-24), `R-OPERATIONAL` (90d fixed), `R-AUDIT` (12mo, 12-24, exportable), `R-BILLING` (7y fixed statutory), `R-ACCOUNT` (account life + 30d).

## 1. ENTITIES

Chain: `SourceMessage -> Candidate -> Draft -> Confirmation -> Task`. Every tenant-owned table carries `workspace_id` **in the primary or composite key**, not as a loose column (ARCHITECTURE §8.1).

**1.1 Workspace** — `R-ACCOUNT`. `id` id PK METADATA req · `name` text IDENTITY req · `slug` text METADATA req **unique** · `tier` enum req `trial|starter|team` · `seats` int req · `billing_customer_ref` text opt (never card data) · `retention_content_days` int req, default 30, range 7-90 · `retention_derived_months` int req, default 12, range 3-24 · `daily_budget_cents` int req · `monthly_budget_cents` int req · `data_region` enum req (v0: US only) · `status` enum req `active|suspended|deleting|deleted` · `created_at`, `updated_at` req, `deleted_at` opt. All non-`name` fields METADATA.
States: `active`<->`suspended` [D]; `active|suspended`->`deleting`->`deleted` (terminal) [D]. Delete cascades to every tenant-owned table **except** `ActionMeter` aggregates and `AuditEvent` (content-free, keep `workspace_id` as reference).

**1.2 Connection** — `R-ACCOUNT`. `id` id PK · `workspace_id` id FK->Workspace req · `kind` enum req `slack|tracker` · `provider` text req · `external_account_id` text req · `external_account_name` text IDENTITY · `scopes_granted` json req · `access_token` text **SECRET** · `refresh_token` text **SECRET** · `token_expires_at` timestamp opt (drives proactive refresh) · `installed_by_member_id` id FK->Member req · `selected_channels` json req — explicit allowlist, **empty means read nothing, and empty is the install default** · `status` enum req `active|degraded|revoked|disconnected` · `last_error_class` text opt — **error class only, never a provider error body** · `created_at`, `updated_at`, `disconnected_at` opt. Unique `(workspace_id, kind, external_account_id)` [D].
States: `active`<->`degraded` (missing scope / token trouble); `active|degraded`->`revoked`; any->`disconnected` (terminal). On disconnect: tokens destroyed immediately, row kept for the audit trail, all `SourceMessage` content for that connection deleted within 24h. Tracker connections also record which projects were mapped; a write to an unmapped project is refused before the API is called (INTEGRATIONS §2.3).

**1.3 SourceMessage** — content `R-CONTENT`, rest `R-DERIVED`. The highest-sensitivity table. `id` id PK · `workspace_id`, `connection_id` id FK req · `external_channel_id` text req · `external_ts` text req (part of the natural key) · `thread_key` text · `author_external_id` text IDENTITY · `author_member_id` id FK->Member **nullable** · `body` text **CONTENT** (nullable after purge) · `body_hash` text req (result caching + dedupe after `body` is gone) · `mentions` json IDENTITY · `permalink` text CONTENT · `has_attachment` bool (attachments never fetched or stored in v0) · `is_bot` bool (pre-filter) · `posted_at`, `ingested_at` timestamp · `content_purged_at` timestamp opt.
Unique/idempotent on `(workspace_id, slack_channel_id, slack_ts)` — upsert, never a duplicate row. Purge: once a candidate decision exists and the workspace window has passed, `body` is nulled and `content_purged_at` set; the row survives as metadata for dedupe, metrics and audit. Messages that produced no candidate may be purged at `R-EPHEMERAL`.

**1.4 Candidate** — `R-DERIVED`, `reason` `R-CONTENT`. `id` id PK · `workspace_id` id req · `source_message_id` id FK req · `batch_id` id req · `kind` enum req `commitment|request|decision` · `confidence` float req (model-reported, calibrated per prompt version) · `reason` text **CONTENT** · `prompt_version` text req · `model` text req · `suppressed_reason` enum **nullable** — `duplicate_open_task|duplicate_draft|below_threshold|filtered|null` · `created_at`. Detection idempotent on `(batch_id, prompt_version)`; results cached on `(content_hash, prompt_version, model)`.

**1.5 Draft** — content `R-CONTENT`, state/ids/timings `R-DERIVED`. `id` id PK · `workspace_id`, `candidate_id` id FK req · `title` text **CONTENT** · `outcome` text **CONTENT** (what "done" means) · `acceptance_condition` text **CONTENT** · `quoted_context` text **CONTENT** (bounded excerpt shown to the confirmer) · `source_permalink` text CONTENT · `suggested_owner_member_id` id FK->Member **nullable — null means "we do not know", which is a valid answer** · `owner_reason` text CONTENT · `suggested_due_date` date **nullable; only when an explicit date appears in the text, never guessed** · `suggested_labels` json CONTENT · `state` enum req `pending|confirmed|rejected|expired|superseded` · `prompt_version`, `model` text req · `expires_at` timestamp req · `created_at`, `updated_at`. Unique: one draft per `(candidate_id, prompt_version)`.
States: only `pending` may transition [D]; `pending` -> `confirmed` | `rejected` (via Confirmation) | `expired` (at `expires_at`) | `superseded` (dedupe / later draft for the same commitment); all four terminal [D]. Dedupe **marks, it does not erase**.

**1.6 Confirmation** — decision `R-DERIVED`, content fields `R-CONTENT`. The evidence that a person authorised a write. `id` id PK · `workspace_id` id req · `draft_id` id FK req **unique** · `member_id` id FK->Member req — **never a service account** · `decision` enum req `confirmed|confirmed_with_edits|rejected` · `edited_fields` json — **field names only, never before/after values** · `edited_payload` json **CONTENT** (final values when edited) · `reject_reason` text CONTENT opt (one word) · `surface` enum req `web|slack_action` · `client_ip_hash` text (hashed, abuse investigation only) · `decided_at` timestamp req. Idempotent on `(draft_id, member_id)`: first confirmation wins, a second returns the same confirmation. Immutable once written [D]; outlives the draft text.

**1.7 Task** — `R-DERIVED`. `id` id PK · `workspace_id` id req · `confirmation_id` id FK **required and unique** · `connection_id` id FK req · `external_task_id` text opt · `external_url` text CONTENT opt · `assignee_member_id` id FK opt · `due_date` date opt · `write_state` enum req `queued|created|failed|needs_review` · `idempotency_key` text req **unique**, derived from `confirmation_id` · `thread_reply_state` enum req `pending|posted|skipped|failed` · `completed_at` timestamp opt (tracker poll/webhook; capture-rate metric) · `created_at`, `updated_at`.
States: `write_state` `queued`->`created` | `failed` (retryable ->`queued`) | `needs_review` (ambiguous write, terminal until a human acts). `thread_reply_state` `pending`->`posted` | `skipped` | `failed`; reply idempotent on `(task_id)`. Deleting a Seros workspace does **not** delete tasks in the customer's tracker.

**1.8 Member** — `R-ACCOUNT`. `id` id PK · `workspace_id` id req · `email` text IDENTITY req (login identity; unique per workspace [D]) · `display_name` text IDENTITY · `role` enum req `owner|admin|confirmer|viewer` · `auth_provider` enum req (v0: email link or password; SSO is v2) · `password_hash` text **SECRET** opt (memory-hard hash, per-user salt, current parameters) · `mfa_enrolled` bool · `is_billable_seat` bool · `status` enum req `invited|active|suspended|removed` · `last_seen_at` timestamp (weekly-active-confirmer metric).
States: `invited`->`active`<->`suspended`; any->`removed` (terminal). On removal, identity fields are cleared and the row kept as a **tombstone** so historical confirmations still resolve to "a person, since removed".

**1.9 Roster / RosterEntry** — `R-ACCOUNT`. Roster (one per workspace, all METADATA): `id`, `workspace_id` **unique**, `last_synced_at`, `sync_state`, `entry_count`. RosterEntry: `id` PK · `workspace_id`, `roster_id` id FK req · `member_id` id FK **nullable** (not everyone in Slack is a Seros member) · `source_external_id` text IDENTITY · `source_handle` text IDENTITY · `tracker_external_id` text IDENTITY · `tracker_handle` text IDENTITY · `mapping_confidence` enum req `explicit|email_match|inferred|unmapped` · `assignable` bool req (admin can exclude people from routing) · `round_robin_cursor` int (fallback fairness). An `inferred` mapping must never be used for an assignment without showing the confirmer what it inferred and why; roster sync must never invent a mapping it is not confident about.

**1.10 ActionMeter** — raw `R-OPERATIONAL` (90d); daily per-workspace per-purpose aggregates `R-BILLING` (7y). `id` id PK · `workspace_id` id req · `purpose` enum req `detect|draft|route|replay|other` · `provider`, `model` text req · `prompt_version` text · `input_tokens`, `output_tokens`, `cached_input_tokens` int · `estimated_cost_micros` int req — priced at call time from a **versioned price table** · `latency_ms` int · `outcome` enum req `ok|timeout|invalid_output|provider_error|budget_blocked` · `ref_type` text, `ref_id` id (what the call was for, so cost is attributable to a draft) · `billable_action` bool · `occurred_at` timestamp req. Contains **no customer content by construction**. A `budget_blocked` row is written whenever the cap refuses a call — blocked calls must be counted.

**1.11 AuditEvent** — `R-AUDIT`, append-only, exportable, content-free by construction. `id` id **monotonic** · `workspace_id` id req · `actor_type` enum req `member|system|operator` · `actor_id` id · `action` text req (`connection.created`, `channel.selected`, `draft.confirmed`, `task.created`, `retention.swept`, `operator.accessed`, ...) · `object_type` text, `object_id` id · `outcome` enum req `ok|denied|failed` · `request_id` text req (correlates with logs) · `detail` json — field names, counts, states, **never values from customer content** · `occurred_at` timestamp req. Rows are never updated or deleted before their retention window, **including on workspace deletion**. A schema-level check plus a test must prove `detail` cannot carry content fields.

## 2. INVARIANTS

**Confirmation (ADR 0002; README rule 1)**
1. "No write to any customer system happens without a recorded human confirmation."
2. The tracker writer accepts a **confirmation id, never a draft id**: "There is no function signature in the system that lets a caller create a task from a draft directly."
3. `Task.confirmation_id` is required and unique — "a task row without one is a schema violation, not a logic bug."
4. A confirmation must reference a `Member` — a real, authenticated person. Service accounts and system actors cannot confirm; an unmapped Slack user cannot confirm (ARCHITECTURE §4).
5. "There is **no configuration flag, environment variable, feature toggle or admin override that disables confirmation** in v0."
6. The permalink reply into the source thread is also a write and is also gated; "nothing is posted at all before a human confirmation" (INTEGRATIONS §1.2). Reactions and confirm-queue messages likewise.
7. Rejections and edits are recorded with the same weight as confirmations — "data, not discards".
8. Any future narrowing (v2 trusted auto-confirm) requires a new superseding ADR.
9. Topology: the only path to a customer's tracker or chat is `API -> Q2 -> tracker writer`; there is no arrow from detection to the tracker (ARCHITECTURE §3).
10. "Degrade toward doing nothing, never toward acting without a human." Every failure path ends in a retry, a hold, or an alert — never in an unconfirmed task (ARCHITECTURE §7).
11. Confirmation is accepted only from an authenticated human session, on two surfaces (`web`, `slack_action`), each running the same authorisation check.

**Logging / content (README rule 2; SECURITY §5; ARCHITECTURE §10)**
12. No customer content in logs, ever. Structured logging with an explicit **allowlist** of fields, not a denylist. Content referenced by id and hash only; errors carry ids, never bodies; a request id on every entry.
13. Every integration error is recorded as a **class**, never as a raw body — provider error bodies can contain customer content.
14. The audit log is append-only and mutable by nobody; `AuditEvent.detail` never carries content values.

**Metering / budget (README rule 3; ADR 0004 §4; ARCHITECTURE §9)**
15. No provider call without an `ActionMeter` row carrying workspace, purpose, model, token counts and estimated cost, "written in the same transaction boundary as the call result". Metering is never optional and never sampled.
16. The provider client is the only thing allowed to open a socket to a model API, and it refuses to run without a meter context.
17. Every outcome is metered, including `timeout`, `invalid_output`, `provider_error`, `budget_blocked`.
18. The budget hard stop is checked **inside the provider abstraction, before the network call** — never in a later reconciliation job. Thresholds: 50% record; 80% internal alert (+ admin if the trend implies a stop); 100% of daily budget = hard stop on model calls for that workspace; plus a global daily spend cap that hard-stops everything and pages on-call.
19. On hard stop: ingest continues and messages are **held, not discarded**; confirmation and tracker writes keep working; in-app and email notice explains exactly what stopped.

**Tenancy (ARCHITECTURE §8; `[[TOM_TENANT_ISOLATION]]`)**
20. `workspace_id` in every tenant-owned key; all access through a **scoped accessor that refuses to build a query without a workspace id**; no ambient "current workspace" global a background job can forget to set.
21. Database row-level security as a second line where supported; the application check stays either way.
22. Cross-tenant queries exist in exactly two audited code paths: aggregate metrics (counts, never content) and the admin console.
23. Encryption keys for connection secrets are per workspace.

**Retention / deletion (DATA-MODEL; `[[TOM_RETENTION_AUTOMATION]]`, `[[TOM_SECURE_DELETION]]`)**
24. Retention is a scheduled sweeper job, per table and per workspace policy, writing a `retention.swept` audit event with counts; alert if a sweep does not run or finds rows past their window.
25. Disconnect: ingest stops immediately, queued detection work for that connection is cancelled, tokens destroyed, that source's stored message content deleted within 24h, cached tracker issue titles deleted, **pending drafts cancelled and never silently confirmed**, audit event + admin email.
26. Two operations must exist and be tested end to end: delete one person's data (clear identity and content fields, keep tombstones) and delete a workspace (dependency order, audit event written last, a completion record the customer can be shown).
27. Content is nulled in place with `content_purged_at` set; metadata survives so audit and billing stay intact. Backups age out rather than being surgically edited.

**Least privilege / scopes (INTEGRATIONS; `[[TOM_RBAC]]`)**
28. Slack bot scopes, and only these: `channels:history`, `channels:read`, `groups:history`, `groups:read`, `users:read`, `users:read.email`, `chat:write`, `commands`, `reactions:write`, `team:read`. **Never** `files:read`, `im:history`, `mpim:history`, `channels:join`, `chat:write.public`, `admin.*`, or any user token.
29. Tracker capabilities only: read projects/boards, read users, read open issues, create an issue, set assignee and due date on the issue being created, attach a source link, receive completion signal. **Never** delete issues, edit issues Seros did not create, or administer the tracker; request only mapped projects where project-scoped grants exist.
30. Read and write use **separate code paths and separate credentials paths** — a bug in dedupe cannot create or modify a task. Dedupe reads the tracker and never writes it.
31. Missing-scope errors degrade a feature and name it; granted scopes are re-displayed on the connection settings page.
32. Roles `owner|admin|confirmer|viewer` enforced on every workspace-scoped read and write; viewer cannot confirm. No standing production access: operator access is break-glass, time-boxed, justified, logged as `operator.accessed`; no bulk export of customer content by any operator path.
33. No model call and no integration call inside a web request — all three model purposes run in workers.
34. Every write carries an idempotency key derived from the confirmation id. On an ambiguous tracker failure the default is **do not retry**: search the tracker for the confirmation id, and if unresolved mark `needs_review` and alert. A duplicate task is a trust incident.
35. Webhooks: verify the Slack signature, reject outside the replay/timestamp window, per-workspace rate limit, body size cap; an unverified request is dropped without processing; acknowledge immediately and enqueue.
36. Minimisation before the provider boundary: pre-filters, bounded context window, pseudonymised authors, no attachments or file contents in v0, no training-permitted terms, provider named on the subprocessor list. Every stage must be safe to run twice.

## 4. MODEL PROVIDER (ADR 0004 — **Proposed, not Accepted**)

Requires:
- **One provider abstraction from the first model call.** No provider SDK type appears anywhere else in the codebase. Single operation `complete` — inputs: prompt version id, rendered messages, response schema, model tier, max input tokens, max output tokens, timeout, workspace id, purpose; outputs: validated structured object, token counts, model id, latency, outcome.
- **Tiers named by role, not vendor**: `cheap`, `standard`, and if needed `careful`. Tier->model mapping lives in versioned configuration with a price per token and is changeable **without a deploy**. Prompts reference tiers; nothing else does.
- **Cheap-model-first cascade.** Pass A on `cheap` over batched messages; only survivors reach `standard` for drafting. Escalation only on explicit conditions — low confidence, schema validation failure, or an evaluation-driven rule — **never by default**, and cascade changes are measured on the golden set first.
- **Metered and budget-checked inside the abstraction**, budget checked **before the network call**; meter rows for every outcome including `budget_blocked` and `provider_error`.
- **Prompts are versioned artefacts**, in files under version control, loaded not concatenated inline; the version is recorded on every `Candidate`, `Draft` and `ActionMeter` row so any suggestion traces to the exact prompt.
- **Every call is bounded**: max input tokens, max output tokens, timeout, retry budget. "An unbounded call is a bug."
- **Structured output validated before it is trusted.** A malformed response is a failed call, not a partial result parsed hopefully: retry once with a stricter instruction, then dead-letter the batch for inspection; never guess at intent.
- **Failure behaviour defined at the abstraction, not the call site**: timeout, bounded retry with jitter, schema validation, dead-letter on repeated invalid output, and a circuit breaker that pauses the detection queue rather than hammering a degraded provider. On outage drafting queues; confirmation and tracker writes keep working.
- **Minimisation before the boundary**: minimum window of text, identities pseudonymised where the task does not require real names.
- **Exit test** (run once before the first paying customer, then twice a year): a second provider implemented (half a day, or the interface has leaked), scored on the golden set for precision/recall/cost per thousand, promoted to `cheap` by a config flip in a canary with no deploy, meter attribution and budget caps re-verified, subprocessor list and customer notification path updated.

Forbids: streaming, tool calling, assistants, files, embeddings and provider-specific parameters in the interface (adding one is a deliberate change for all implementations, or the feature does not ship); naming any provider as chosen in this repository; any provider whose terms do not exclude customer content from training, "whatever it costs or scores"; model calls inside a web request; unmetered calls; unbounded calls; escalation to a higher tier by default.

## 5. TESTING

Split: **deterministic code gets assertions; model behaviour gets measurements and thresholds.** **No test may require a live model provider or a live third-party API** — the suite runs offline, in CI, on an aeroplane.

Deterministic coverage required before the first customer: webhook verification (unsigned, wrongly signed or replayed rejected without processing); idempotency for every key in ARCHITECTURE §6 (no duplicate `SourceMessage`, no duplicate `Draft`, **above all no duplicate task in the tracker**); confirmation gate (no path creates a task without a `Confirmation` referencing a real member — by construction *and* a test that attempts it and expects failure); tenancy (two populated workspaces, every read returns only the requester's rows, plus a **static check that fails the build** on any tenant-owned query with no workspace predicate); authorisation (each role does exactly what its matrix row says; viewer cannot confirm); logging hygiene (a content-classed value through the log formatter must not appear in output); metering (every simulated provider call produces **exactly one** meter row, including failures, timeouts and budget blocks); budget caps (refuse before the network call, write `budget_blocked`, leave confirmation and writes working); retention (nulls content at the configured age, writes the audit event, leaves metadata intact); deletion (removes every content and identity field, retains content-free audit and billing rows, completes within the promised window); integration failures (429, 5xx, timeout, revoked token, missing scope) against recorded fakes only.

**Golden set.** A fixed corpus of chat threads labelled with which messages contain a `commitment`, `request` or `decision`, who the owner should be, and what the task should say. Composition (ASSUMPTION): clear commitments 25%, requests to a named person 15%, decisions with an implied action 10%, **hard negatives 30%** (hypotheticals, jokes, past tense, quoting someone else, "we should probably…"), ambiguous where two humans disagree 10%, end-to-end noise threads 10%. Size: start at **200 labelled messages across at least 20 threads**, grow to 1,000 (below ~200 the confidence interval is wider than any improvement measured). Labelling: two labellers on the first 100 items with disagreements **recorded, not resolved away** (inter-labeller agreement is the model's ceiling); a written label guide; labels versioned with the set and results **never compared across versions**. Provenance and consent recorded per entry; anything without either is ineligible.

**Anonymisation (non-negotiable):** written consent naming the purpose and excluding training use; a pipeline, not find-and-replace (consistent per-thread pseudonyms, stable placeholders for company and client names, replaced URLs/file names/identifying numbers, dates shifted by a constant per-thread offset); a human reads every thread before it enters the corpus; the corpus lives in a separate restricted private repository; a partner can withdraw, which forces baselines to be **re-run, not adjusted**. **Ordinary test fixtures are always synthetic**; the consented corpus is evaluation-only.

**Metrics and gates:** detection precision at message level — **must not regress against the established baseline**; recall — reported, deliberately not optimised in v0; owner suggestion accuracy (share of suggested owners a human accepted unchanged) — reported per workspace; abstention rate — reported (falling abstention with flat accuracy is a warning); cost per thousand messages — reported every run; per-thread capture reported alongside message-level numbers. No absolute precision/recall number is set — the first run establishes the baseline and the baseline may not fall. A change raising recall and lowering precision is rejected by default; overriding needs a written reason in the PR. Roadmap-inherited exits: acceptance above 60% across at least three non-founder workspaces; a scripted, timed end-to-end run signup->first confirmed task under 30 minutes before every release, **release blocked if exceeded**; evaluation cost/1k vs the production meter must not disagree by more than a factor of two; integration error rate under 1% with per-connection error-class counters.

**Determinism:** fix the sampling temperature and every other decoding parameter for evaluation and record them; score the same run twice on a subset to record the model's own variance — **a change smaller than that variance is not a change**; evaluation runs recorded in an append-only log (date, corpus version, prompt version, model, results, cost). Every prompt PR must attach: golden set version, model and tier, precision/recall/abstention before and after with deltas, cost per thousand before and after, and a sample of the decisions that flipped in both directions. No prompt reaches production without an offline evaluation run attached.

**Contract tests:** recorded real responses, scrubbed of content and tokens, replayed in CI (this is what the suite runs), plus a nightly live contract test against sandbox accounts doing the real loop (read history, create a task, set assignee, post a reply, delete the test task), asserting shapes and status codes, never content, never in a customer workspace.

**Release stages:** Local (full offline suite + evaluation run; no precision regression) -> CI (plus docs checks, secret scanning, dependency alerts; a red build never merges) -> founder workspace (24h, no unexplained rejection spike) -> canary workspaces, two or three consenting partners (48h, acceptance within normal variance, no integration error spike) -> general. **Prompt version is a property of a workspace, not of a deploy**, so canarying works and rollback is a flag flip. Watch per canary after any model-affecting change: acceptance, rejection, edit rate, drafts per thousand messages, abstention, cost per action; a rejection spike is a rollback, not a discussion. Not tested: exact model output strings, load/performance beyond a smoke check, browser matrix, third-party APIs themselves, anything needing production data.

## 6. OPEN QUESTIONS forced on a first implementation

1. **Which tracker is v0?** Undecided (design-partner question). Gates the writer, the dedupe read path, the roster mapping and every scope string in INTEGRATIONS §2; near-irreversible for six months.
2. **Language, runtime, database, queue, cloud** — ADR 0003 open; no product is named anywhere in the spec.
3. **Model provider and the `cheap`-tier model** — ADR 0004 is *Proposed, not Accepted*; no provider chosen, and `estimated_cost_micros` needs a versioned price table that does not exist.
4. **Is `SourceMessage.body` stored at all after detection**, or only `body_hash` plus the bounded excerpt copied into the draft? "The single biggest privacy design choice in the model"; trades replay/evaluation ability against privacy and cost.
5. **Are tracker labels and titles cached locally for dedupe, or read live each time?** Caching is faster and cheaper; live reading stores less customer content.
6. **Structured rejection taxonomy in v0** (wrong owner, not a task, duplicate, already done) versus `reject_reason` as a free word — worth much more for v1 routing, costs one dropdown now.
7. **Retention defaults are drafts** and must be reconciled with the published privacy policy before launch; the legal pack binds. Same for `[[DELETION_SLA_DAYS]]`, `[[BACKUP_RETENTION_DAYS]]`, `[[RETENTION_SECURITY_LOGS]]`, `[[BREACH_NOTICE_HOURS]]`.
8. **Does routing need a model call at all in v0**, or does a roster heuristic plus explicit-mention parsing suffice? Determines whether `purpose=route` rows ever exist.
9. **Default confirm surface — web app or Slack?** Both are in scope; the default shapes onboarding and notifications. Related: message action, modal, or both (the modal is what allows editing before confirming).
10. **Is per-workspace prompt versioning built in v0?** Listed as open, but §7 of the testing strategy and the rollback story already assume it.
11. **Completion signal: webhook or polling?** Drives `Task.completed_at` and, if webhook, another inbound endpoint to secure.
12. **Second labeller for the first 100 golden-set items**, and whether any design partner consents to a corpus at all; if none do, the corpus is synthetic plus founder data and the evaluation ceiling is lower.
13. **Release cadence** — continuous deployment with canary flags or a weekly train; the rollback procedure depends on it.
14. Unspecified but needed to write code: batch window sizes beyond the ASSUMPTION, the confidence floor, `Draft.expires_at` duration, retry counts and dead-letter N, `body_hash` and `client_ip_hash` algorithms, id type (uuid vs monotonic), whether `AuditEvent` ids must be globally or per-workspace monotonic, and every transition marked `[D]` above.
